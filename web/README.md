# Versal Folha TXT Web

Fundação da fase 1: API FastAPI, base React/TypeScript/Vite e PostgreSQL.
Requisitos: Docker Engine com Compose v2; para execução sem containers,
Python 3.12+ com `venv` e Node.js 24 com npm.

## Executar com Docker

Na pasta `web/`:

```bash
cp .env.example .env
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

Preencha `POSTGRES_PASSWORD` e `JWT_SECRET_KEY` em `.env` com valores diferentes,
gerados pelo comando acima. Use a senha hexadecimal sugerida: caracteres especiais
em senhas exigem codificação na URL do PostgreSQL. Não versione `.env`.

```bash
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 180
bash tests/smoke_compose.sh
```

Frontend: http://localhost:5173. API: http://localhost:8000.
Documentação OpenAPI: http://localhost:8000/docs.
O health check retorna `{"status":"ok"}` e verifica apenas a disponibilidade HTTP;
a rota de saúde não acessa o banco. O serviço `migrate` executa Alembic após o
PostgreSQL ficar saudável; a API aguarda sua conclusão e o frontend aguarda a API.
`migrate` terminar com código 0 é esperado. Falha de migração bloqueia a API;
consulte `docker compose logs migrate` e corrija a causa antes de repetir a subida.
O smoke aguarda os três serviços saudáveis, confere a revisão Alembic no banco e
consulta `/health` e o HTML do frontend pelas portas publicadas. Requer Bash,
Python 3 e Docker no host; não cria usuários nem altera dados.

Use `http://localhost:5173` no navegador, mantendo o mesmo hostname da API para
cookies e CORS. `BACKEND_PORT` e `FRONTEND_PORT` podem ser definidos em `.env`
para evitar conflitos (padrões 8000 e 5173); a URL pública da API e a origem CORS
acompanham essas portas. Dentro da rede Compose, a API acessa `db:5432`; o
navegador acessa `localhost`, não os nomes internos dos serviços.

Após subir, crie o primeiro administrador seguindo o
[bootstrap explícito](backend/README.md#primeiro-administrador-de-desenvolvimento).
Nenhuma conta ou senha padrão é criada automaticamente.

```bash
docker compose logs -f
docker compose down
```

O volume `postgres_data` preserva os dados ao parar a stack. Alterar a senha em
`.env` depois da primeira inicialização não altera a senha do banco já criado.
Este Compose serve ao desenvolvimento local; o frontend usa o servidor do Vite.

Para uma instância separada com conversão do SQLite, veja o
[guia de conversão e primeiro acesso](docs/local-conversion-instance.md).

## Backend sem Docker

Na pasta `web/backend/`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Em Debian/Ubuntu, o comando `venv` requer o pacote `python3.12-venv`.
Preencha `JWT_SECRET_KEY` com pelo menos 32 caracteres e `DATABASE_URL` com a URL
do PostgreSQL disponível no seu ambiente. O Compose não publica a porta do banco.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Os testes usam uma chave exclusiva de teste. Sem `TEST_DATABASE_URL`, os testes de
integração PostgreSQL são pulados; configuração, saúde e metadados continuam verificáveis.

## Frontend sem Docker

Na pasta `web/frontend/`:

```bash
cp .env.example .env
npm ci
npm run dev
```

Para verificar TypeScript e gerar os arquivos estáticos:

```bash
npm run build
```

Execute `npm test -- --run` para os testes de componentes e sessão.
`npm run test:e2e` verifica o shell responsivo com Playwright (requer seus navegadores).

`VITE_API_BASE_URL` aponta para a API consumida pela sessão e pelos cadastros. Variáveis `VITE_*` são públicas e não
devem conter segredos.

Os módulos de plano de contas e rubricas são descritos no
[guia de cadastros contábeis](docs/accounting-catalogs.md).

## Banco de dados e migrações

A migração `0001` cria as 13 tabelas da fundação. O processo da API não cria tabelas. A subida Compose aplica as migrações pelo
serviço `migrate`; para conferir ou reaplicar explicitamente, na pasta `web/`:

```bash
docker compose build migrate
docker compose run --rm migrate
docker compose exec backend python -m alembic current
```

Sem Docker, na pasta `web/backend/`, com `DATABASE_URL` e `JWT_SECRET_KEY`
configurados no ambiente ou no `.env`:

```bash
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m alembic check
```

Os identificadores e vínculos são inteiros de 64 bits (`BIGINT`), compatíveis
com os IDs do SQLite original. As PKs usam `GENERATED BY DEFAULT AS IDENTITY`,
permitindo importar os IDs existentes e gerar novos IDs depois de sincronizar
as sequências. As sete tabelas operacionais mantêm nomes e campos do desktop,
incluindo competência textual (`10/2026`), status, CPF/CNPJ com a formatação
existente e os dados históricos de cada linha de folha. Campos nulos e
repetições aceitos no esquema original continuam aceitos. As tabelas novas de
usuários, sessões, arquivos e auditoria são acréscimos da versão web.

Timestamps novos usam timezone; `valor` e `liquido` usam `NUMERIC` sem escala fixa/`Decimal`, como no original,
sem arredondamento imposto pela migração.
As FKs `RESTRICT` protegem o histórico e verificam o vínculo entre folha/importação
e empresa. A futura migração deverá conferir referências órfãs, divergências
entre empresas antes de importar; o SQLite original não
impunha essas FKs. Detalhes: [compatibilidade do esquema](docs/legacy-schema-compatibility.md).

A migração é estática e reversível. `downgrade base` remove as tabelas e seus dados;
use essa reversão somente em ambientes descartáveis.

Para verificar migração, reversão, reaplicação e todos os testes contra PostgreSQL
16 descartável, sem alterar o banco da aplicação, execute na raiz do repositório
(com Docker disponível e a `.venv` do backend preparada):

```bash
bash web/backend/tests/run_postgres.sh
```

O script usa porta local dinâmica e armazenamento temporário, removendo o container
ao terminar. Para outro Python, defina `PYTHON_BIN` com caminho absoluto.
Também é possível testar contra um banco de testes já migrado com
`TEST_DATABASE_URL=postgresql+psycopg://... .venv/bin/python -m pytest -q`.
Cada teste de integração desfaz suas alterações em uma transação; nunca use o
banco operacional como banco de testes. O gerador `get_db()` encerra a sessão e
reverte alterações não confirmadas; os serviços confirmam explicitamente suas transações.

## Autenticação

As rotas `/api/v1/auth` aceitam JSON e estão documentadas em `/docs`:

- `POST /login`: recebe `{"email":"usuario@example.com","password":"..."}` e
  retorna `access_token` e `token_type: "bearer"`.
- `GET /me`: recebe `Authorization: Bearer <access_token>` e retorna
  `id`, `email`, `role` e `is_active`, sem hashes ou tokens de sessão.
- `POST /refresh`: usa o cookie para emitir um novo access token e rotacionar
  o refresh token. O token anterior deixa de ser válido.
- `POST /logout`: revoga a família da sessão e apaga o cookie; retorna `204`.

Senhas usam Argon2id. Access tokens duram 15 minutos por padrão; refresh tokens,
7 dias, conforme `ACCESS_TOKEN_EXPIRE_MINUTES` e `REFRESH_TOKEN_EXPIRE_DAYS`.
O refresh token é opaco e somente seu hash SHA-256 é armazenado no banco.
Ele nunca aparece no JSON: fica no cookie `refresh_token`, com `HttpOnly`,
`SameSite=Lax` e caminho `/api/v1/auth`. Com `ENVIRONMENT=production`, o cookie
exige HTTPS (`Secure`). No frontend, usar `credentials: 'include'` e guardar
apenas o access token em memória. CORS usa as origens explícitas de
`FRONTEND_ORIGINS`, separadas por vírgula; o frontend já usa esse fluxo de sessão.

Reutilizar um refresh revogado invalida toda sua família. Usuários inativos
não podem entrar, renovar sessão ou acessar `/me`. Logout não revoga JWTs já
emitidos: eles expiram no prazo configurado. Login, refresh, logout e reutilização
são auditados sem credenciais, na mesma transação das alterações de sessão.
As operações de refresh/logout são serializadas por usuário no PostgreSQL.
`tests/test_auth_concurrency.py` verifica refresh/refresh e ambas as ordens de
refresh/logout com requisições e conexões independentes, observando o bloqueio
real no PostgreSQL. O script `tests/run_postgres.sh` inclui esses testes. Eles
confirmam respostas, auditoria, revogação persistida e rejeição dos sucessores.

Não há cadastro público. O comando explícito de criação do primeiro administrador
é restrito ao desenvolvimento, exige credenciais no ambiente e está documentado
no [guia do backend](backend/README.md#primeiro-administrador-de-desenvolvimento).
Os testes usam contas sintéticas e banco descartável; a stack operacional não
é populada automaticamente.

## Autorização e administração

Todas estas rotas exigem `Authorization: Bearer <access_token>`:

| Rota | Permissão e comportamento |
| --- | --- |
| `GET /api/v1/users` e `GET /api/v1/users/{user_id}` | Administrador; retorna identidades sem hashes ou tokens. |
| `POST /api/v1/users` | Administrador; recebe `email`, `password` (12–1024 caracteres), `role` e `is_active` opcional. Retorna `201`. |
| `PATCH /api/v1/users/{user_id}` | Administrador; altera os mesmos campos, todos opcionais; rejeita corpo vazio e valores nulos. |
| `DELETE /api/v1/users/{user_id}` | Administrador; inativa o usuário preservando histórico e vínculos. Retorna `204`. |
| `GET /api/v1/users/{user_id}/companies` | Administrador; lista os IDs das empresas vinculadas ao usuário. |
| `PUT /api/v1/users/{user_id}/companies/{company_id}` | Administrador; concede vínculo. Retorna `204`, inclusive se já existir. |
| `DELETE /api/v1/users/{user_id}/companies/{company_id}` | Administrador; revoga vínculo. Retorna `204`, inclusive se já estiver ausente. |
| `GET /api/v1/companies` | Lista somente empresas vinculadas ao usuário autenticado. |
| `GET /api/v1/companies/{company_id}` | Exige vínculo explícito, inclusive para Administrador. |

Papéis aceitos: `Administrador`, `Contador`, `Operador` e `Consulta`. O papel
precisa existir no banco; o bootstrap de desenvolvimento cria os quatro papéis. E-mails são validados e preservados exatamente como informados,
seguindo a comparação exata usada no login. Usuários novos começam sem vínculos.
Campos extras são rejeitados; email duplicado retorna `409`.

Ausência de sessão válida ou usuário inativo retorna `401`. Falta de papel
permitido ou de vínculo retorna `403`; a consulta de empresa sem vínculo também
retorna `403` quando o ID não existe, sem revelar sua existência. Alvos inexistentes
na administração retornam `404`. Papel, atividade e vínculos são consultados no
servidor a cada requisição, incluindo requisições com access tokens anteriores
à alteração. Mudanças de senha preservam sessões existentes.
Alterar papel ou inativar o último administrador ativo retorna `409`, sem
alteração nem auditoria. Administradores inativos não contam como substitutos.
Essa verificação é serializada no PostgreSQL para impedir que duas mudanças
concorrentes eliminem todo acesso administrativo.

Cada alteração administrativa é confirmada junto com sua auditoria (ator, IP,
entidade e empresa quando aplicável), sem senhas ou hashes. Falha na auditoria
reverte a alteração; concessões e revogações sem mudança não criam eventos.
Empresas e colaboradores possuem CRUD com validação de CPF/CNPJ, escopo por
empresa e auditoria transacional. A exclusão com histórico preserva os registros.

## Estado e limites operacionais

Login, renovação de sessão, rotas protegidas e telas de Dashboard, Empresas e
Colaboradores estão integrados. O token de acesso fica em memória; recarregar a
página tenta renovar a sessão pelo cookie. Usuários e vínculos são administrados
pela API. A competência do cabeçalho é uma seleção local; indicadores reais e
listagem de competências ainda aguardam endpoints. Os demais módulos do menu
apresentam sua indisponibilidade nesta fase.

Este ambiente é local, sem TLS, servidor de produção ou backup operacional.
Parser PDF/XLS/XLSX, importação completa, validação contábil completa, exportação
TXT Siagri/Aliare, restauração e migração automática do SQLite não estão implementados.
O desktop continua sendo o sistema operacional durante a conferência.

Antes de extrair parsers ou exportadores, siga o
[protocolo de equivalência](docs/parser-equivalence-strategy.md) e as
[regras das fixtures](backend/tests/fixtures/README.md).
A preservação de IDs, vínculos e sequências está detalhada no
[contrato de esquema](docs/legacy-schema-compatibility.md).

Para validar uma stack separada, escolha portas livres e um projeto exclusivo:

```bash
BACKEND_PORT=18000 FRONTEND_PORT=15173 docker compose -p versal-check up --build -d --wait --wait-timeout 180
BACKEND_PORT=18000 FRONTEND_PORT=15173 bash tests/smoke_compose.sh -p versal-check
docker compose -p versal-check down
```

Esse projeto tem seu próprio volume. `down` preserva os dados; use `down --volumes`
somente para descartar um projeto de testes cujo conteúdo possa ser removido.
Nunca execute testes ou reversões de migração contra o banco operacional.
