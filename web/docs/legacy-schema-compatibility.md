# Compatibilidade com o banco desktop

A referência é o DDL de `DB.init()` em `versal_folha_txt_v2_18/app.py`, linhas
325–331, consultado em 2026-10-16. A fixture `backend/tests/fixtures/legacy_schema.sql`
contém somente esse esquema, sem registros do cliente. Não executamos o desktop
nem abrimos seu banco em modo de escrita.

| Tabela original | Estrutura mantida |
| --- | --- |
| companies | ID, código SIAGRI, razão, fantasia, CNPJ e status |
| employees | ID/company_id, nome, CPF, matrícula, cargo, centro de custo, código de correntista e status |
| rubrics | ID/company_id, código/descrição/tipo, contas, histórico, status e quatro flags contábeis |
| chart_accounts | ID/company_id, conta/descrição, centro de custo e flags de correntista |
| finance_params | ID/company_id, tipo, documento, parceiro, contrapartida, centro de custo, vencimento, histórico e ativo |
| imports | ID/company_id, competencia textual, arquivo, data_hora e status |
| payroll_lines | ID/import_id/company_id, CPF, nome, cargo, verba, referência, valor, tipo e líquido |

Os nomes físicos são os originais. Aliases de atributos Python, como `Company.name`
para `razao`, não criam ou renomeiam colunas. O esquema aceita CPF/CNPJ pontuados,
campos nulos e repetições que o desktop permitia. Linhas de folha continuam guardando
os dados históricos, sem vínculo obrigatório com o cadastro de colaboradores ou rubricas.

O PostgreSQL usa `BIGINT GENERATED BY DEFAULT AS IDENTITY`: IDs de 64 bits como no
SQLite, aceitando os valores antigos explicitamente. Nenhum mapeamento para UUID
é necessário. As seis tabelas novas (`roles`, `users`, `user_companies`,
`refresh_tokens`, `stored_files`, `audit_logs`) atendem recursos web e também têm
PKs inteiras. `refresh_tokens.family_id` é um UUID de agrupamento de sessões novas,
sem relação com os identificadores do desktop.

Há acréscimos: timestamps com timezone, metadados opcionais de arquivo/ator em
importações e FKs restritivas, incluindo o vínculo empresa/importação da folha.
`valor` e `liquido` usam `NUMERIC` sem escala fixa, como no esquema original,
para preservar os decimais sem impor arredondamento. O banco antigo não impunha FKs. Antes da futura migração real, será necessário conferir
referências órfãs e divergências de empresa. Nenhum registro será descartado ou renumerado silenciosamente.
Novos cadastros terão validação nos serviços, sem alterar os dados históricos nesta etapa.

Após copiar os IDs, cada sequência deve ser sincronizada em uma janela sem novas
inserções. Exemplo para `companies` (repetir para cada tabela importada):

```sql
SELECT setval(
    pg_get_serial_sequence('companies', 'id'),
    GREATEST(COALESCE(MAX(id), 1), 1),
    COUNT(*) > 0
) FROM companies;
```

A revisão da migração `0001` substitui o esquema UUID do PR #2 ainda aberto. A versão
anterior foi testada apenas em PostgreSQL descartável; esta revisão não converte
bancos UUID existentes. Não há importador de dados reais nesta entrega.

Execute `bash web/backend/tests/run_postgres.sh` na raiz para verificar o esquema,
copiar registros sintéticos de SQLite para PostgreSQL preservando todos os campos,
IDs e vínculos, verificar geração de novos IDs após a carga e testar
reversão/reaplicação da migração.
